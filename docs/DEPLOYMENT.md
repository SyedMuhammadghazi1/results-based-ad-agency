# Deployment

The app is a stateless Next.js standalone server plus PostgreSQL 16. Any container host works;
Vercel works too. Everything below assumes HTTPS in front of the app.

## 1. Build artefacts

```bash
docker build -t outcome-ads --build-arg NEXT_PUBLIC_APP_NAME="Outcome Ads" .
```

The image (node:22-alpine, non-root `nextjs` user, `HEALTHCHECK` on `/api/health`) contains:

| Command                                 | Purpose                                                                    |
| --------------------------------------- | -------------------------------------------------------------------------- |
| `node server.js` (default)              | The web app on `$PORT` (3000)                                              |
| `node migrate.mjs`                      | Apply the committed SQL migrations in `/app/drizzle` to `$DATABASE_URL`    |
| `node job.mjs <job> [--period=YYYY-MM]` | Run a background job once (alternative to HTTP cron)                       |
| `node rotate-secrets.mjs`               | Re-encrypt stored integration secrets after rotating `DATA_ENCRYPTION_KEY` |

Behind a TLS-intercepting corporate proxy, pass its CA only for the install step:
`docker build --secret id=extra_ca,src=/path/ca.crt .` (never baked into a layer).

CI publishes `ghcr.io/<owner>/<repo>:<git sha>` and `:latest` on every push to `main`
(`.github/workflows/deploy.yml`).

## 2. Configuration

Set every variable from `.env.example` (validated at start-up by `src/env.ts`; the container exits
with a clear message if something is missing). Production minimums:

- `APP_URL` (https), `DATABASE_URL` (+ `DATABASE_SSL=true` for managed Postgres)
- `BETTER_AUTH_SECRET` (`openssl rand -base64 48`), `DATA_ENCRYPTION_KEY` (`openssl rand -base64 32`),
  `DATA_ENCRYPTION_KEY_ID`, `CRON_SECRET`
- `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`
- `SMTP_*`, `EMAIL_FROM`
- `AD_CONNECTOR_FALLBACK=manual` until real ad-platform credentials are approved (the sandbox
  connector must never drive real clients)

### Client IP behind your proxy

Rate limits (sign-in, sign-up, password reset, tracking, apply form), the audit log, agreement
acceptance and sessions use the client IP. It is resolved in exactly one place
(`src/lib/client-ip.ts`) from **one** of:

- `CLIENT_IP_HEADER` — a single header your platform sets and clients cannot spoof. Only that
  header is read (first value).
- `TRUSTED_PROXY_HOPS` (default `1`) — when no header is configured: the number of proxies in front
  of the app that append to `X-Forwarded-For`. The client IP is the entry that many positions from
  the right; anything further left was sent by the client and is ignored. `0` never trusts it.

| Host                                                    | Setting                                                                |
| ------------------------------------------------------- | ---------------------------------------------------------------------- |
| Vercel                                                  | `CLIENT_IP_HEADER=x-real-ip`                                           |
| Fly.io                                                  | `CLIENT_IP_HEADER=fly-client-ip`                                       |
| Cloudflare (proxied DNS) in front of any host           | `CLIENT_IP_HEADER=cf-connecting-ip` — and only accept Cloudflare's IPs |
| Render, Railway, Heroku, a single nginx / load balancer | `TRUSTED_PROXY_HOPS=1` (the default)                                   |
| Two proxies (e.g. CDN → load balancer → app)            | `TRUSTED_PROXY_HOPS=2`                                                 |
| Container reachable directly, without a proxy           | Not recommended; `TRUSTED_PROXY_HOPS=0` (no per-IP limits)             |

nginx must append (`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`) or overwrite
(`$remote_addr`) the header. A wrong setting either trusts a client-controlled value or yields no
IP: without an IP, endpoints that also limit per account or per tracking key (sign-in, sign-up,
password reset, `/api/track/touch`) rely on those limits alone and the app logs
`could not resolve a trusted client IP` once per process. IPv6 clients are rate limited per /64.

Store secrets in the host's secret manager. Keep `DATA_ENCRYPTION_KEY` backed up separately from
database backups — without it, stored integration secrets are unrecoverable.

## 3. Database & migrations

Migrations are plain SQL generated by drizzle-kit and committed in `drizzle/`. Apply them **before**
starting a new version (they are written to be additive/backwards compatible):

```bash
docker run --rm -e DATABASE_URL -e DATABASE_SSL=true ghcr.io/<owner>/<repo>:<sha> node migrate.mjs
# or from a checkout:
DATABASE_URL=... npm run db:migrate
```

The deploy workflow runs this automatically with `secrets.PRODUCTION_DATABASE_URL` in the
`production` environment, then calls `secrets.DEPLOY_HOOK_URL`.

## 4a. Container hosts (Render, Fly.io, Railway, ECS, Kubernetes, a VM)

- Image: `ghcr.io/<owner>/<repo>:<sha>`; port 3000; health check path `/api/health`
  (liveness) and `/api/ready` (readiness, checks the DB).
- **Render**: create a Web Service from the image, add a "Deploy Hook" and store its URL as the
  GitHub secret `DEPLOY_HOOK_URL`. Pre-deploy command: `node migrate.mjs`.
- **Fly.io**: `fly launch --image ghcr.io/...`; `[deploy] release_command = "node migrate.mjs"`;
  `[[http_service.checks]] path = "/api/health"`.
- **Railway**: deploy from the image; set the start command to `node server.js` and a pre-deploy
  command `node migrate.mjs`; use a Railway deploy webhook for `DEPLOY_HOOK_URL`.
- Run ≥ 2 instances for availability — sessions, rate limits and locks all live in Postgres.

## 4b. Vercel + managed Postgres (e.g. Neon)

1. Create a Neon project; use the **pooled** connection string for `DATABASE_URL` and set
   `DATABASE_SSL=true` and a small `DATABASE_POOL_MAX` (e.g. 3) because each serverless instance
   has its own pool.
2. Import the repo in Vercel (framework: Next.js). Add all env vars. `output: "standalone"` is
   ignored by Vercel and is harmless.
3. Run migrations from CI (deploy workflow with `PRODUCTION_DATABASE_URL`) or locally with
   `npm run db:migrate` before promoting a deployment.
4. `vercel.json` declares the cron schedule; Vercel Cron calls `GET /api/cron/<job>` with
   `Authorization: Bearer $CRON_SECRET` automatically when `CRON_SECRET` is set. Long jobs are capped
   by the plan's function duration (`maxDuration = 300` is set) — at larger scale move jobs to a
   container (`node job.mjs`).

## 5. Stripe (agency account — performance fees)

1. Create restricted or secret API keys → `STRIPE_SECRET_KEY`.
2. Add a webhook endpoint `https://<APP_URL>/api/webhooks/stripe` with events:
   `checkout.session.completed`, `invoice.finalized`, `invoice.paid`, `invoice.payment_failed`,
   `invoice.voided`, `invoice.marked_uncollectible` → signing secret `STRIPE_WEBHOOK_SECRET`.
3. In Billing settings enable automatic retries (Smart Retries) and customer emails for failed
   payments as desired; our dunning job pauses campaigns after `DUNNING_GRACE_DAYS`.
4. Tax: invoices currently carry **no sales tax / VAT**. Decide with an accountant whether to enable
   Stripe Tax (and add `automatic_tax` to invoice creation) before billing real customers.
5. Local testing: `stripe listen --forward-to localhost:3000/api/webhooks/stripe`.

Client Stripe accounts (revenue sources) are separate: each client adds a webhook in _their_
Stripe account pointing at `/api/webhooks/client-stripe/<integration id>` (shown in the app).

## 6. Scheduled jobs

| Job                     | Schedule (UTC)       | Purpose                                                        |
| ----------------------- | -------------------- | -------------------------------------------------------------- |
| `budget-guard`          | hourly (`5 * * * *`) | Refresh today's spend, pause at the cap, resume in a new month |
| `sync-spend`            | daily 04:15          | Pull the last 3 days of spend per campaign                     |
| `dunning`               | daily 07:30          | Pause campaigns for invoices overdue > `DUNNING_GRACE_DAYS`    |
| `cleanup`               | daily 03:45          | Expired sessions, limiter rows, old webhook/job logs           |
| `monthly-billing`       | 1st of month 06:00   | Statements + Stripe invoices for the previous month            |
| `weekly-revenue-report` | Mondays 13:00        | One-number email to each client                                |

Trigger with `POST https://<APP_URL>/api/cron/<job>` and `Authorization: Bearer $CRON_SECRET`
(Vercel Cron: `vercel.json`; GitHub Actions: `.github/workflows/cron.yml` with `vars.APP_URL` and
`secrets.CRON_SECRET`; or any scheduler / `node job.mjs <job>`). All jobs are idempotent, so retries
and overlapping runs are safe; `monthly-billing` additionally accepts `?period=YYYY-MM` to re-bill a
specific month (it will only fill gaps, never duplicate).

## 7. Ad-platform API access (honest status)

- **Meta Marketing API**: create a Meta app (Business type), add Marketing API, request
  `ads_management` and `ads_read` (and `business_management`) with **App Review** and **Business
  Verification**; until approved only app roles/test ad accounts work. Set `META_APP_ID`,
  `META_APP_SECRET`, OAuth redirect `https://<APP_URL>/api/oauth/meta/callback`. Long-lived user
  tokens expire (~60 days) — reconnect from the operator console or move to a System User token.
- **Google Ads API**: needs a Google Cloud OAuth client (`GOOGLE_ADS_CLIENT_ID/SECRET`, redirect
  `https://<APP_URL>/api/oauth/google/callback`, the `adwords` scope requires OAuth app verification)
  and a **developer token** from a manager account with **Basic or Standard access** — a new token
  is test-accounts-only. Set `GOOGLE_ADS_LOGIN_CUSTOMER_ID` when accessing clients through your MCC.
- **TikTok**: no connector yet — campaigns use the `manual` connector (operators act in TikTok Ads
  Manager, spend is not synced automatically).

The real connectors are covered by unit tests with mocked HTTP only; validate them against sandbox /
test accounts before relying on them (see LAUNCH_CHECKLIST).

## 8. Backups

- Enable automated daily backups + point-in-time recovery on the managed Postgres (Neon history
  retention, RDS PITR, Render/Railway backups). Target RPO ≤ 24h (≤ 5 min with PITR).
- Additionally take a logical dump before every release that contains migrations:
  `pg_dump --format=custom --no-owner "$DATABASE_URL" > backup-$(date +%F).dump`.
- Test a restore quarterly (see RUNBOOK). Keep `DATA_ENCRYPTION_KEY` (all ids still referenced)
  with the backups' access policy but stored separately.
